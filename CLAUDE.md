# Carepatron growth challenge: findings site

You are building a single-page website that presents Andre Nwofor's submission for the Carepatron AI Growth Marketer internship. It will be judged directly on its quality by Carepatron's growth team. It must be premium, clear at a glance, and scrupulously accurate.

The brief is in `reference/challenge-brief.txt`. The full written findings are in `reference/1-findings.md`, `reference/2-journey-and-email.md` and `reference/3-how-i-used-ai.md`. The site's job is to make those points simpler, clearer and more visual, not to add new ones.

---

## 1. Non-negotiables (read before every change)

1. **No false data.** Every number on the site comes from `data/findings.json` (generated by `analysis/analysis.py` from the raw CSVs). Never invent, estimate, extrapolate or "round for effect" beyond normal rounding.
2. **Never edit `data/findings.json` or `data/findings.js` by hand.** If a number you need is missing, stop and tell Andre. The fix is to add it to `analysis/analysis.py` and regenerate, never to type it in.
3. **Every claim maps to the claims register** in `content/copy-and-claims.md` (§2). If a sentence isn't backed by a claim there, don't write it. Follow the wording rules (§1) and banned claims (§3) exactly: no causal language, no projections, no fake users or testimonials.
4. **Keep the caveats.** Simpler doesn't mean less honest. The confidence labels (High / Medium / Low), the correlation-not-cause note and "the data is fictional" all stay on the page.
5. **Independent work.** No Carepatron logo or brand assets. The site says it is an independent submission by Andre Nwofor and not an official Carepatron site.
6. **Ask before big decisions.** Plan first, show Andre, then build. Don't deploy without his go-ahead.

## 3. How data reaches the page

- Load `data/findings.js` with a plain `<script>` before your own scripts; read `window.FINDINGS`. (No fetch, so it works on GitHub Pages and when opened from disk.)
- Bind numbers in the copy with a data attribute and a tiny formatter, for example:
  `<strong data-f="dropoff.never_back_after_day0_pct" data-fmt="pct0">45%</strong>`
  The static text inside the element is the fallback, so the page is complete at rest even before JS runs; it must equal the formatted value (the verifier checks it).
- Charts read their values from `window.FINDINGS` only. No data values typed into chart code.
- Formatters to provide: `pct0` (45%), `pct1` (12.4%), `int` (518), `int,` (1,075), `or` (2.4), `ci` (9.8–15.5%).

## 4. Design direction

**Audience and feel.** A growth team and a hiring manager who skim. It should feel like a confident product-launch page crossed with a well-made data story: calm, precise and premium. Avoid template looks (purple-to-blue gradient heroes, neon on black, cream and terracotta, emoji section markers, everything centred, the same rounded card everywhere).

**Colour: innovation and trust.** A starting palette; refine it, but keep the roles:
| Token | Value | Role |
| --- | --- | --- |
| `--ink-900` | `#0A1A2F` | deep navy: trust. Hero and dark bands, primary text |
| `--ink-700` | `#1D3354` | secondary dark surfaces |
| `--paper` | `#F6F8FB` | cool off-white page background |
| `--surface` | `#FFFFFF` | panels |
| `--line` | `#DCE3ED` | rules, gridlines |
| `--muted` | `#5A6B85` | secondary text, "other" data in charts |
| `--signal` | `#0FB5A6` | innovation accent. In charts it means only "the three key actions / real client work / success" |
| `--cobalt` | `#3D63F5` | interactive UI only (links, buttons, focus) |
| `--caution` | `#E8A33D` | caveats only, used sparingly |

Colour meaning is consistent across every chart: signal = the key actions or success, grey = everything else, caution = caveats. Check contrast (WCAG AA) on both light and navy bands.

**Type.** Display: Sora (600/700), used with restraint. Body: IBM Plex Sans. Numbers and labels: IBM Plex Mono with tabular figures. All from Google Fonts with system fallbacks. A clear scale; headings `text-wrap: balance`; body at about 65 characters per line.

**Layout.** Max width about 1200px, generous whitespace. A sticky top nav with the five section names and a reading-progress indicator. Each section opens with a numbered eyebrow matching the brief's numbering ("01 · Read the data"), a headline that states the point (not the topic), one main visual, and at most three short paragraphs. Hero size fits its content; don't use a full-viewport hero.

**Motion.** GSAP 3 with ScrollTrigger from cdnjs (pin an exact version, e.g. 3.12.5). One orchestrated moment per section: charts draw in as they enter, stat count-ups run once, the journey steps through on scroll, the phone slides in. Respect `prefers-reduced-motion` (show final states, no animation). Content is never hidden waiting for an animation: the page must read fully with JavaScript off.

**Charts.** D3 v7 from cdnjs (pinned, e.g. 7.9.0) or hand-built SVG. For every chart:
- the title states the finding with its number ("45% of trials never come back after day 0");
- bars start at zero; show 95% intervals wherever the copy mentions them;
- label only the few points the message rests on;
- a source line under it: "Carepatron sample data (fictional) · 518 practices · events in days 0–14 before payment" (adjust the window per chart);
- accessible: `role="img"`, an `aria-label` with the finding, and a visually hidden table or text summary of the values;
- readable at 375px wide (simplify, or switch orientation, on small screens).

**Imagery.** No stock photos, and no fake screenshots of Carepatron's real interface. Illustrative mock-ups (the phone showing the email, the Open Slot demo) are fine.

## 6. Open Slot (the tool)

- Source: `tool/open-slot.html`. It was written for a host that adds the document wrapper, so create `tool/index.html` by adding `<!doctype html>`, `<html lang="en">`, a `<head>` with charset, viewport and the existing `<title>`/fonts/styles, and `<body>` around the content. Keep all functionality: live outputs, tone switch, services editor, QR card, copy buttons.
- You may restyle it to match the site's tokens, but test every feature afterwards.
- Embed it in Ship something with a same-origin `<iframe src="tool/" title="Open Slot booking-link kit" loading="lazy">`, responsive height, plus an "Open the full tool" link.
- Its QR library loads from `https://cdn.jsdelivr.net/npm/qrcode-generator@1.4.4/qrcode.js`; keep that exact version.

## 7. Verification gates (all must pass before deploy)

1. `python3 analysis/analysis.py --check` reports OK.
2. `python3 analysis/verify_site.py index.html assets/js/*.js tool/index.html` reports 0 numbers needing review. If a flagged number is genuine context (not data), add it to `CONTEXT_NUMBERS` with a comment saying why, and list it in `verification.md`. Never "fix" a flag by editing findings.
3. Rendered check: serve the site (`python3 -m http.server 8000`), dump `document.body.innerText` after animations finish (Playwright if available) to a file, and run `python3 analysis/verify_site.py --text <file>`.
4. Claims review: write `verification.md`, a table of every sentence on the page that states a number or a finding, mapped to its claim ID in `content/copy-and-claims.md`. Search the page for banned words (cause, drive, lead to, boost, increase, "more likely", guarantee, "will convert") and fix any hit.
5. Visual QA: screenshots at 375, 768, 1280 and 1440px; check reduced motion; keyboard through the nav, the A/B toggle and the tool; no horizontal scroll; Lighthouse mobile scores of 90+ for performance and accessibility.
